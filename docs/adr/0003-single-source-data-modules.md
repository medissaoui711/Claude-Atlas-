# ADR-0003: هيكلة محتوى الأطلس كـ TypeScript Modules ثابتة

## الحالة (Status)
معتمد (Accepted)

## التاريخ (Date)
2026-09-19

## السياق (Context)
يحتوي أطلس كلود على محتوى معرفي ضخم يشمل عشرات المفاهيم المعمارية، مئات النقاط التعليمية، التمارين التطبيقية، أسئلة التحقق، والأوامر الطرفية. كان التحدي هو كيفية تخزين هذه البيانات وهيكلتها بحيث تضمن:
1. الفحص الصارم للأنواع (Type Safety).
2. سهولة الإثراء والتعديل دون لمس كود الواجهات.
3. تفادي تأخير طلبات الشبكة (Zero Latency).

## القرار (Decision)
هيكلة البيانات كـ **TypeScript Modules نقية وثابتة** داخل مجلد `src/data/`، مع ربط كل كائن بواجهات دقيقة معرفة في `src/types.ts`، واستخدام تقنية دمج الإثراء المعرفي (`capabilitiesEnrichment.ts`) عبر المفتاح الفريد `id`.

## البدائل التي درست (Alternatives)
1. **ملفات JSON منفصلة**:
   - *سبب الاستبعاد*: ملفات JSON لا توفر فحصاً صارماً للأنواع أثناء الكتابة، وتتطلب خطوات استيراد أو معالجة إضافية.
2. **قاعدة بيانات SQLite / Headless CMS**:
   - *سبب الاستبعاد*: تتطلب إعداد شبكي أو خادم وسيط ومزامنة، مما يتعارض مع بساطة التطبيق واستقلاليته.

## التبعات (Consequences)
- **الإيجابيات**:
  - اكتشاف أي خطأ في الحقول أو الأنواع لحظة كتابة الكود وأثناء تشغيل `npm run lint`.
  - سرعة فائقة؛ البيانات متوفرة فوراً في الذاكرة دون عمليات `async/await` أو شاشات انتظار (Loading spinners) مزعجة.
  - إمكانية إضافة أو تعديل أي مفهوم للمنظومة بمجرد إضافة كائن في مصفوفة.
- **السلبيات**:
  - تضخم حجم حزمة البناء قليلاً (يمكن حلها مستقبلاً بالـ Code Splitting إذا زاد المحتوى أضعافاً مضاعفة).
